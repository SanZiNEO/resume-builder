# 简历构建：人机协作核心流程

## 这个 Skill 是什么

这不是一份“项目工具说明书”。  
它定义的是 AI 与人协作生成简历的**流程和行为准则**。

真正的核心是：

> AI 先理解项目，再理解现有简历，然后像访谈一样一个个板块问用户，边问边记录，最后统一处理样式，再构建给用户看。

## 适用时机

- 用户说“帮我做一份简历”
- 用户说“帮我更新简历”
- 用户开始描述自己的经历、项目、实习、工作
- 用户想补充某个板块
- 用户想基于现有简历重新整理

## 核心原则

1. **先理解，再提问。**
2. **有现有简历就先读懂，不重复问已经清楚的信息。**
3. **逐个 YAML 板块问，不要一次性把所有内容一起问完。**
4. **多用 ask 工具刨根问底。**
5. **边问边记录。**
6. **每完成一个 YAML，就处理它的 body 内容。**
7. **最后才写个人总结和技能板块。**
8. **内容全部完成后，再统一处理样式/排版/主题。**
9. **不虚构经历，所有数字都要有出处或用户确认。**
10. **遵守 privacy、reference 和用户红线。**

## 工作流

### 阶段 0：理解项目

先读：

- 项目 README
- 目录结构
- 已有 skill / 子文档
- `make.py` 的用法

理解：

- 数据放在哪里
- 布局 / 样式 / 主题怎么组织
- YAML 协议是什么
- 当前项目处于什么状态

### 阶段 1：理解现有简历

如果不存在现有简历：

```text
跳过此阶段
```

如果存在：

```text
1. 读 data/{person}/ 下所有 YAML
2. 读每个文件的 reference
3. 理解已有内容、口径、红线、数字来源
4. 不重问已有且清晰的信息
5. 只针对遗漏、模糊、矛盾的地方提问
```

### 阶段 2：前置问题

在开始逐板块访谈前，先问少量前置问题：

- 这份简历的使用场景（校招 / 社招 / 作品集 / 投递方向）
- 目标岗位 / 求职方向
- 是否有偏好风格（可后置）
- 是否有必须包含或必须不写的内容

这些问题的目的是确定方向，不展开细问。

### 阶段 3：内容访谈

这是核心阶段。

#### 3.1 逐个 YAML 问

不要一次性生成所有板块。  
按一个 YAML 一个 YAML 的方式来：

```text
选择一个板块
→ 向用户提问
→ 追问细节
→ 记录回答
→ 写入该 YAML
→ 处理 body 内容
→ 再进入下一个板块
```

#### 3.2 提问方式

- 多用 `ask_user_question` 工具
- 每次问一个明确的问题
- 根据回答继续追问
- 对模糊数字、时间、角色、成果要追问到底
- 对“不知道/没做过”不要硬编

#### 3.3 边问边记录

每问到一个关键信息，就记录到：

```text
当前 YAML
当前 YAML 的 reference
或 notes/ai-collaboration-log.md（如果存在）
```

记录内容包括：

- 用户原话 / 事实
- 数字和来源
- 口径
- 后续待确认事项

#### 3.4 完成一个 YAML 后处理 body

每个 YAML 的 content 完成基本采集后：

```text
把原始经历整理成 body 条目
检查是否有数字
检查是否有可验证成果
检查是否与已有口径一致
```

### 阶段 4：收尾板块

内容访谈的最后，才写：

```text
个人总结（summary）
技能（skills）
```

原因：

- 总结和技能需要基于前面所有经历来提炼
- 先问经历，后写总结，不容易空洞
- 技能要能从真实经历里找到依据

### 阶段 5：统一样式 / 排版

所有内容 YAML 完成后：

1. 再统一选择风格 / 主题 / 布局
2. 构建 HTML 预览
3. 给用户看效果
4. 根据用户反馈调整

细节见子文档：

```text
style-layout.md
```

### 阶段 6：校验、构建、交付

```text
1. 跑 make.py validate
2. 构建 HTML（可选 PDF / PNG）
3. 给用户看最终效果
4. 根据反馈迭代
5. 用户确认后再提交 git
```

## 红线（核心）

- 不虚构经历
- 不虚构数据
- 不替用户做关键决策
- 不把未经确认的数字写进简历
- 不泄露隐私
- 不忽略已有 reference 中的口径
- 用户没有确认前不提交 git
